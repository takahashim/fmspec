# 詳細化の検査、対称性による削減、定数の掃引の計画

TLA+とTLCの機能のうち、fmspecに加える価値の高い3つについて、何を保証し、どこを作り、何を証明するかを書く。
別の作業者や別のセッションが引き継げるように、決めた方針と、まだ決めていないことを分けて書く。
仕様書（[ruby_model_checker_spec.md](../ruby_model_checker_spec.md)）の節番号は「仕様書§」で示す。

## 結論

| 機能 | 判断 | 段階 | 判定ゲートへの影響 | 証明の追加 |
|---|---|---|---|---|
| 定数を変えた繰り返し検査（掃引） | 加える。最初に行う | 4の拡張（Ruby DSL） | なし | なし |
| 詳細化の検査（refinement checking） | 加える | 7と8の後（合成、プロセス、移行の上に載せる） | 判定の種類を1つ加える | 小〜中。証明書の帰納法の延長 |
| 対称性による状態の削減（symmetry reduction） | 加える。前提の量化の評価順は決め、実装した | 9（性能改善） | 証明書の意味が変わる | 大。意味論の対称性の定理が要る |

着手の順は、掃引、詳細化、対称性とする。

- 掃引は判定の意味に触れず、Ruby側だけで完結する。対称性の効果を測るベンチマークのモデル（要素数を2、3、4と変える）にもそのまま使える。
- 詳細化の証明は、既存の `lemma_reach_in_cert`（`cert.rs`）と同じ形の帰納法で済む。遷移列挙の健全性と完全性はすでに証明済みなので、それを抽象モデルの側にも使う。
- 対称性は効果が最も大きいが、証明が最も大きい。後述の「量化と評価エラーの順序」の問題を先に決めないと、定理が成り立たない。

## 1. 定数を変えた繰り返し検査

実装済み（`lib/fmspec/builder.rb` の `constant`、`lib/fmspec/model.rb` の `with` と `sweep`、`test/constants_test.rb`）。
使い方は [dsl.md](../dsl.md) の「定数を変えた検査」にある。

### 目的

TLCの `.cfg` で定数を差し替えるのにあたる。
fmspecは定数を一般化した証明をしないので、「capacity が2、3、4のそれぞれで成り立つ」を手軽に確かめられることに実用上の価値がある。
各組み合わせの検査は独立した普通の検査で、判定の意味は変わらない。
結果の表示では「指定した値ごとに検査した」ことだけを述べ、定数一般についての主張はしない。

### 決めた方針

**Ruby側で、組み合わせごとにモデルを作り直す。**
定数の値で状態の型が変わること（`int(0..capacity + 1)`）や、プロセスの数が変わること（`process :incr, count: n`）が多いからである。
IRの定数だけを差し替える方式では、型やプロセスの展開に定数を使えない。

- `constant` は、上書きを反映した値をRubyの値として返す。今は `nil` を返すので、戻り値を使う既存の仕様はなく、互換性は保たれる。
- `Fmspec.define` が返すモデルは、定義のブロックを保持する。`with` は上書きを渡してブロックを実行し直し、新しいモデルを返す。
- `sweep` は値の直積を作り、組み合わせごとに `with` と検査を行う。結果は組み合わせと結果の対の列である。
- 宣言していない定数の上書きと、型に合わない値は `Fmspec::BuildError` にする。
- 組み合わせごとにIRが違うので、`model_digest` も違う。保存した反例や証明書を別の値のモデルに使うと、判定ゲートが拒否する。

```ruby
Tickets = Fmspec.define(:tickets) do
  capacity = constant :capacity, 3
  state :sold, int(0..capacity + 1), initial: 0
  # ...
end

Tickets.with(capacity: 4).check.verified?
Tickets.sweep(capacity: 2..4).each { |values, result| puts "#{values} #{result.status}" }
```

### まだ決めていないこと

- 合成した仕様での上書きの書き方（`Shop.with(stock: { capacity: 4 })` のように接頭辞で指定するか）。今は `Fmspec::BuildError` にし、合成する前の仕様を `with` で作り直してもらう。
- CLIの扱い。CLIはIRを受け取るので、掃引はRuby側の機能とする。型に定数を使わないモデルに限って、CLIで定数を差し替える選択肢（`--const capacity=4`）は後で検討する。
- 結果の表示。今はすべての組み合わせを検査し、組み合わせと結果の対の配列を返す。失敗した組み合わせの要約の表示や、最初の失敗で止める選択肢は後で検討する。

### 確認すること

- 上書きのない `with` が、元のモデルと同じIRを作る。
- `sweep` の各要素の結果が、その値で直接定義したモデルの結果と一致する。
- 型に合わない値、未宣言の定数の上書きを拒否する。

## 2. 詳細化の検査

実装済み。中核は `crates/fmspec-core/src/refine.rs`（検査器、判定ゲート `decide_refinement`、補題）と `model_lower.rs` の `lower_model_map`（写像の下ろし）、
読み込みは `crates/fmspec-ir/src/refinement.rs`、探索器は `crates/fmspec-search/src/refine.rs`、APIとCLIは `fmspec refine`、DSLは `Fmspec.refinement`（`lib/fmspec/refinement.rb`）である。
使い方は [dsl.md](../dsl.md) の「詳細化の検査」、文書の形式は [ir.md](../ir.md) の「詳細化」、定理は [verification.md](../verification.md) にある。

実装で決めたこと：

- 判定の型（`RefVerdictKind`）を安全性の判定と分けた。`Refines` は、具体モデルの証明書が帰納的で、具体モデルが検査条件のもとで安全（到達可能な評価エラーがない）で、`refines` が成り立つことを述べる。
- 具体モデルの評価エラーは、主張 `RefClaim::Model`（安全性のトレースの主張と同じもの）で `Error` にする。写像の評価の失敗は `RefClaim::Map` で `Error` にする。
- 写した状態で抽象モデルの遷移列挙が評価エラーになり、移れるかを決められないときは、探索器が `Inconclusive`（理由 `abstract_failed`）を返す。判定ゲートは、移れないと示せた遷移だけを `NotRefines` にする。
- 詳細化の検査では、具体モデルの不変条件、遷移契約、デッドロックは検査しない（検査条件は対象の操作だけを選ぶ）。
- 抽象モデルの操作は、すべてを照合に使う。

まだ行っていないこと：

- 写像の式について、値の意味論との対応の証明（`lemma_safe` にあたるもの）。今の定理は、下ろした中核の式について述べる。
- 出力と操作名の対応の照合。
- 証拠の検査の資源上限（`max_check_cost`）。検査器は、具体モデルの遷移ごとに抽象モデルの遷移を列挙し直す。
- 外部から提示した詳細化の証明書とトレースの検査（`verify-certificate` と `replay` にあたるもの）。
- DSLの写像のブロックから、プロセスの状態（`s.incr[0].pc`）と定数を参照すること。

### 目的

実装寄りの具体モデル B が、抽象モデル A の正しい実装になっていることを確かめる。
例えば、Railsの決済フローを細かく書いたモデルが抽象的な残高のモデルを守ること、ロックで区切ったプロセスの実装が atomic な操作の仕様を守ること、移行の各段階が旧仕様の観測できる振る舞いを保つことである。
今は、合成（compose）の後に横断的な不変条件を書くしかなく、A の不変条件を B の言葉で書き直す必要がある。

### 保証する性質

利用者は、写像 f（refinement mapping）を、A の状態変数ごとに B の状態上の式として与える。
判定ゲートが受理したときに成り立つ性質 `refines(B, cB, A, f)` は次である。

1. B の到達可能な状態 s で、f(s) の評価は失敗せず、A の状態の型に属する。
2. B の初期状態 i について、f(i) は A の初期状態である。
3. B の到達可能な状態からの有効な遷移 s → t について、f(t) = f(s)（状態の変わらないステップ）であるか、A のある操作・引数・内部選択で f(s) から f(t) に遷移できる。

ここから、B の有限の振る舞いを f で写し、状態の変わらないステップを除くと、A の振る舞いになる。
系として、A の不変条件 P が A で成り立つなら、P ∘ f は B の到達可能な状態で成り立つ。
A 側の判定（A の証明書による `Verified`）と組み合わせるときは、A の検査条件の対象操作が、3で照合に使った操作をすべて含むことを確かめる。

保証しないもの：

- 活性と公平性の保存。TLA+の詳細化は活性を含むが、仕様書§2.2のとおり対象外とする。B が A の操作を永遠に先延ばしにしても検出しない。
- 出力と操作名の対応。3は状態だけを照合する。出力を照合する選択肢（操作の対応表を与え、出力の一致も要求する）は後で検討する。MBTと組み合わせるときに要る。

### 決めた方針

**判定ゲートの検証済みの関数として作る。**
仕様書§12.6の方針に従えば、A の guard と更新を f で置き換えた式を B の遷移契約にして、既存の安全性の検査に帰着させることもできる。
しかしその置き換えはRuby側の未検証の変換になり、A の意味論についての定理にならない。
判定ゲートで f(s) を検証済みの評価器で求め、A の後続を検証済みの遷移列挙で再計算すれば、定理は A の `RawModel` の意味論について直接述べられる。
証明も、既存の帰納法の延長で済む。

**判定の型を分ける。**
`decide_refinement(b, cb, a, mapping, ev)` を、`decide` と並ぶ前提条件のない公開関数にする。
事後条件は `refinement_sound`（`verdict_sound` と同じ形）とし、判定の型も別にする。
詳細化の `Verified` を、B の安全性の `Verified` と取り違えないためである。

**証拠は既存のものを使う。**

- 受理側：B の証明書 C（今と同じ、B の遷移で閉じた状態集合）。検査器は C の各状態 s で f(s) を評価し、各有効な遷移 s → t で f(t) を評価して、f(t) = f(s) か、A の f(s) からの後続に f(t) が含まれることを確かめる。探索器の記録した対応は使わない。
- 違反側：B のトレースと、新しい主張 `RefinementInit`、`RefinementStep`、`MappingError`。トレース検査器は今と同じくトレースを再生し、末尾で主張を確かめる。`RefinementStep` は、最後の遷移の像が状態の変わらないステップでなく、A の後続のどれでもないことを確かめる。これは A の遷移列挙の完全性に依る（証明済み）。
- f(s) で A の遷移列挙が評価エラーになる場合は、保守的に受理しない。B に到達可能な状態があっても、A がその状態で壊れているからである。

**IRは、2つのモデルと写像を持つ新しい文書にする。**
写像の式は B の状態の上で型を付け、結果の型は A の状態変数の型とする。
下ろしは不変条件と同じ経路を使い、複合型の状態変数はスロットごとの式にする。
下ろしの全域性の計画（[lowering_totality.md](lowering_totality.md)）の成果がそのまま使える。

### 証明すること

| 証明義務 | 内容 | 場所の案 |
|---|---|---|
| Refinement Certificate Soundness | B の証明書と上の検査を受理したなら、`refines(B, cB, A, f)` が成り立つ | `refine.rs`（新規）。`lemma_reach_in_cert` と同じ到達の帰納法 |
| Refinement Trace Validity | トレースを受理したなら、そのトレースは B で有効で、末尾で主張どおりに詳細化が破れる | `trace.rs` の延長 |
| Refinement Gate | `decide_refinement` は前提条件を持たず、`refinement_sound` を満たす | `gate.rs` の延長 |
| 不変条件の移送 | `refines` と A の `safe` から、P ∘ f が B の到達可能な状態で成り立つ | 系として `refine.rs` |

ソースの意味論との対応は、`lemma_safe`（`model_safe.rs`）と同じく、2つのモデルの下ろしの意味保存から得る。
写像の式の意味保存は、不変条件の意味保存と同じ補題で示せる見込みである。

### DSLの案

```ruby
Ledger = Fmspec.define(:ledger) do
  state :balance, int(0..10), initial: 0
  action(:deposit, amount: 1..3) { |s, amount| update balance: s.balance + amount }
  invariant(:non_negative) { |s| s.balance >= 0 }
end

PaymentsRefinesLedger = Fmspec.refinement(Payments, Ledger) do
  map(:balance) { |s| s.wallet + s.settled }
end

PaymentsRefinesLedger.check.verified?
```

### 確認すること（受入基準の案）

| 入力 | 期待結果 |
|---|---|
| A を A 自身へ恒等写像で写す | `Verified` |
| B の操作が A の状態を変えない（写像の像が変わらない） | 状態の変わらないステップとして受理し `Verified` |
| B から guard を1つ削除し、A にない遷移ができる | `RefinementStep`。最短の反例を判定ゲートで再生できる |
| B の初期状態の像が A の初期状態でない | `RefinementInit`、0ステップ |
| 写像の像が A の状態の型の範囲外 | `MappingError` |
| 遷移を欠いた B の証明書 | 後続状態欠落で拒否 |
| §12.4のロックなしカウンタ（2プロセス）を、atomic な increment の仕様へ写す | `RefinementStep`（更新の消失） |

### まだ決めていないこと

- 写像の像の重複計算の扱い。検査は B の辺ごとに A の列挙を行うので、f(s) ごとに A の後続をまとめて計算するとよい。この表は検証済みの側に置く必要がある。
- 写像が評価エラーになる到達可能な状態の報告を、`Error` と同じ扱いにするか、詳細化の違反として扱うか（案：`MappingError` は違反でなく評価エラーとして報告する）。
- 移行（migration）で、段階ごとに異なる写像を与える書き方。

## 3. 対称性による状態の削減

実装済み。ただし、実装した設計はこの節の当初の案と違う。当初の案（対称な列挙型と、値の意味論での対称性の定理）は残し、その後に「実装した設計」を置く。

### 実装した設計

対称性を、列挙型の値の置換ではなく、**状態変数のブロックの入れ替え**として宣言する（プロセスのインスタンス、`symmetric [:pc_a, :seen_a], [:pc_b, :seen_b]`）。
読み込み（`fmspec-ir`）は、隣り合うブロックの入れ替えごとに、状態のスロットの置換 `p`（対合）を作る。
判定ゲート（`gate.rs` の `decide_symmetric`、`sym.rs`）は宣言を信用せず、入れ替えごとに次を確かめる（`swap_maps`、`sym_ok`）。

- `p` は対合で、入れ替える2つのスロットは同じ型を持つ。
- 各操作を、スロットの添字を `p` で付け替えた操作が、モデルの中にある（構文として一致する）。操作の対応は対合で、検査条件の対象の操作を対象の操作に写す。
- 不変条件と遷移契約も同じく、付け替えたものがモデルの中にあり、対応は対合で、対象を対象に写す。
- デッドロック検査をするときは、終端条件が付け替えで変わらない。

構文の一致から意味の対称性を導くのは、`lemma_rename_eval`（式の評価は、スロットの付け替えと、状態の入れ替えで可換）である。
これは中核の式（下ろした後の式）についての補題で、値の意味論や列挙型を経由しない。
当初の案で問題になった量化の評価順は、この設計では効かない（量化の本体の評価の順は変わらない）。量化の変更（案A）は、このPRで別に行った。

代表元の証明書の検査（`check_sym_certificate`）は、各状態の後続を遷移列挙で計算し直し、後続を `canonicalize`（隣り合う入れ替えを、状態が辞書順で小さくなる限り施す）で代表元にして、証明書に含まれることを確かめる。
`lemma_sym_safe`：入れ替えがどれも対称性で、証明書が「初期状態と、各状態の後続が、入れ替えの列で証明書の状態に移れる」を満たすなら、モデルは安全である。
判定の意味は `decide` と同じ `verdict_sound` で、`Verified` はモデルが安全であることを述べる。

違反側の証拠は変えない。探索器（`fmspec-search/src/sym.rs`）は、代表元の経路から、各ステップの入れ替えを逆にたどって具体的なトレースを作り、事象を具体的な状態で評価し直して主張にする。トレースは今のトレース検査器が検査する。

インスタンスをまたぐ不変条件（`count >= 終えたインスタンスの数` など）は、付け替えると別の式になる。
読み込みは、対称性を宣言したモデルの各不変条件に、入れ替えの像を元と同じ名前の不変条件として加える（`close_invariants`）。
モデルが対称なら、不変条件とその像は、すべての到達可能な状態で同時に成り立つので、検査する性質は変わらない。像を加えたモデルが対称であることは、判定ゲートが確かめる。

まだ行っていないこと：

- 列挙型の値の置換としての対称性（Mapのキーや引数のドメインの要素を入れ替えるもの）。当初の案の「対称な型」にあたる。
- 対称性による削減を使う検査での、証明書の書き出しと外部の証明書の検査、`max_check_cost`。
- 終端条件、遷移契約の像の自動追加。プロセスの既定の終端条件（すべてのインスタンスが `:done`）は付け替えで式が変わるので、デッドロック検査と対称性は同時に使えない。
- 合成した仕様への対称性の宣言の引き継ぎ。

### 目的

ユーザー、注文、ジョブのように、入れ替えても区別のない要素を、状態空間から割る。
状態数は要素数の階乗で効くので、扱えるモデルの大きさが大きく変わる。
TLCは利用者の対称性の宣言を検査せずに信用するが、fmspecは対称性が成り立つことを判定ゲートの側で保証する。
この点がTLCとの違いになる。

### 対称な型と構文の条件（当初の案）

列挙型に `symmetric: true` を付けて、対称な型を宣言する（MurφのscalarsetやTLCのモデル値の集合にあたる）。

```ruby
user = enum(:user, :u1, :u2, :u3, symmetric: true)
```

対称な型の値は、次の使い方だけを許す。IR検証（中核）で検査する。

- `eq` と `ne`、集合の要素、写像のキーと値、組やOptionの要素。
- 型全体についての量化と、型全体を引数のドメインにした操作。
- 順序の比較、整数への変換、ラベルのリテラルは、操作、不変条件、遷移契約、終端条件、定数では使えない。初期状態ではリテラルを使ってよい（後述のとおり、初期状態は対称でなくてよい）。

### 量化と評価エラーの順序（案Aに決め、実装した）

今の量化は、値の正規順にたどり、結果が決まった時点で打ち切る（`quant.rs`）。
この評価順は、対称性を壊す。
例えば `forall u: P(u)` で、P(u1) が偽、P(u2) が評価エラーのとき、正規順では偽を返す。
u1 と u2 を入れ替えた状態では、先に評価エラーに当たる。
そのため、「s で評価が成功するなら、σ(s) でも成功し、結果は σ で写した値になる」が成り立たず、`Verified` が主張する「到達可能な評価エラーがない」を σ(s) について言えない。

仕様書§18は量化の評価順を未決事項にしていた。
対称性に着手する前に、量化の意味を評価順に依らない形に決める。

- 案A（採用）：`forall` は、偽になる要素があれば偽、なければ評価エラーになる要素があれば評価エラー、なければ真とする。`exists` も同様に、真が評価エラーに勝つ。偽（`exists` では真）での打ち切りはそのまま使える。打ち切れないのは評価エラーに当たったときだけで、その後の要素の評価を続ける。
- 案B：評価エラーになる要素があれば、常に評価エラーとする。打ち切りができなくなり、遅い。
- 案C：対称な型の量化の本体に、評価エラーにならないことを静的に要求する。判定が難しく、利用者に説明しにくい。

案Aに決めた。

- 決まる値（`forall` では偽、`exists` では真）に当たったら、その値を返し、残りを評価しない。
- 評価エラーに当たったら、そのエラーを保留して、残りの要素の評価を続ける。後で決まる値に当たれば、その値を返す。
- たどり終えたとき、保留したエラーがあれば、最初に保留したエラー（正規順で最初の要素のエラー）を返す。なければ、`forall` は真、`exists` は偽を返す。

評価エラーになるかどうかと、成功したときの値は、たどる順に依らない。
どの種類のエラーを報告するかは、たどる順に依る。
対称性の定理は「評価エラーになるかどうか」と「成功したときの値」について述べればよく、エラーの種類までは要らない。

この変更は、対称性を使わないモデルの判定も変える。
今は評価エラーになる量化が、後ろに決まる値の要素を持つ場合、その値になる。
例えば `forall x in {0, 1}: 10 / x < 5` は、今は0での除算で評価エラーだが、変更後は `x = 1` で偽になる（`10 / 1 < 5` が偽）。
したがって、今は `Error` になるモデルが、`Verified` や `Violated` になることがある。
逆に、今は成功する評価が、評価エラーになることはない（打ち切る位置は、決まる値の最初の要素で変わらないため）。
変更は意味論の変更として、それだけを1つのPRでレビューする（仕様書§14.3）。

#### 変更した箇所

意味論は中核と参照実装に複数の写しがあり、比較テストが一致を検査しているので、一度に変えた。

### 保証する性質と証拠

σ を対称な型の値の置換とし、状態、引数、出力に要素ごとに作用させる。
集合と写像は、置換したあと正規形に並べ直す。

証明書 C は、軌道の代表元の集合でよい。検査器は次を確かめる。

1. 各初期状態 i について、ある置換 σ で σ(i) が C に含まれる。
2. C の各状態 s で、不変条件が成り立ち、各有効な遷移 s → t で遷移契約が成り立ち、ある置換 σ で σ(t) が C に含まれる。
3. 指定されている場合、C の各状態でデッドロックがない。

検査器は、σ(t) を求める正規化の関数を持つが、証明するのは「返す値が、ある置換 σ についての σ(t) である」ことだけでよい。
正規形が一意であることは、受理の完全性（探索器と同じ代表元を選ぶこと）にしか効かず、健全性には要らない。
正規化が探索器とずれても、拒否になるだけで、誤った `Verified` にはならない。
要素数が小さいうちは、すべての置換を試して辞書順で最小のものを選ぶ実装で足りる。

違反側の証拠は変えない。
探索器が代表元の上で見つけた経路から、各ステップの置換を逆にたどって具体的なトレースを作り、今のトレース検査器に渡す。
したがって、`Violated` と `Error` の経路には新しい証明が要らない。

### 証明すること

| 証明義務 | 内容 |
|---|---|
| Symmetry Validation | 構文の条件を検査する関数の健全性 |
| Semantic Symmetry | 構文の条件を満たすモデルで、式の評価が置換と可換である。`eval(σ(s), e) = σ(eval(s, e))`（評価エラーも含めて）。遷移の集合も置換で写り合う |
| Encoding Equivariance | 状態の符号化が置換と可換である。`enc(σ(v))` は、符号化列に対する置換の作用（スロットの入れ替えとラベルの付け替え、集合と写像の並べ直し）で `enc(v)` から得られる |
| Reduced Certificate Soundness | 上の検査を受理し、モデルが対称なら、`safe(m, c)` が成り立つ |

Semantic Symmetry は、中核の下ろした式ではなく、ソースの意味論（`source.rs`、`smodel.rs`）で示す。
下ろした式には列挙型が残っておらず、置換を述べにくいからである。
中核の安全性との対応は、`lemma_safe` で移す。
Encoding Equivariance は、検査器がスロットの列の上で置換を計算するために要る。`encoding.rs` と `canon.rs` の延長になる。

最も大きいのは Semantic Symmetry で、式の種類ごとに場合分けが要る。
量化の意味を案Aに変えた後でなければ、このとおりには成り立たない。

### 範囲の外とするもの（最初の版）

- 対称性と詳細化の同時使用（写像 f も対称である必要がある）。
- MBTの候補集合での利用。
- 部分的な対称性（要素の一部だけを入れ替えられる場合）、複数の対称な型の組み合わせ以外の置換群。

### 確認すること

- 3ユーザーの注文のモデル（`bench/models.rb` の `orders` をユーザーについて対称にしたもの）で、状態数がおよそ 1/3! になり、判定が削減なしと一致する。
- 対称でない使い方（ラベルのリテラル、順序の比較）を含むモデルで `symmetric: true` を拒否する。
- 代表元でない状態を含む証明書、代表元の後続を欠いた証明書を拒否する。
- 削減ありの探索で見つけた反例が、具体的なトレースとして判定ゲートで受理される。
- 掃引で要素数を2、3、4と変え、削減の効果を `docs/performance.md` に記録する。
