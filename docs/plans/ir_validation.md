# IRの読み込みの変換検証

## 目的

`fmspec-ir` は、IRのJSONを読み、名前を解決したモデル（`SModel`）と名前の表を組み立てる。
今は、ここが証明の外にあり、信頼基盤に含まれる（`docs/verification.md` の「信頼基盤」）。
型の合わない木を作る誤りは中核の `check_model` が拒否するが、型は合うが意図と違うモデルを作る誤り（同じ型の状態変数の取り違え、演算子の取り違え、局所変数の束縛の取り違えなど）は検出できない。

`fmspec-ir` の名前解決そのものは証明せず、組み立てた結果が入力のJSONと対応することを、検証済みのコードで確かめる（変換検証）。
対応を、IRの各構文が `SModel` のどの構造になるかを直接書いた spec の関係 `ir_rel` として定義し、これをIRの意味の定義とする。
`fmspec-ir` に誤りがあっても、入力と対応しないモデルは内部エラーとして拒否する。

## 定理

中核に、JSONの木（`Json`）、名前の表（`IrNames`）、`SModel` を受け取り、対応を確かめてから下ろす関数 `load_checked` を置く。

- `load_checked(j, ns, sm)` が `Ok(m)` を返すなら、`ir_rel(j, ns, sm)` が成り立ち、`lowers_model(sm, m)` が成り立つ。
  したがって、判定ゲートの定理と合わせて、`m` の検査の結果は、`j` が表すモデルの値の意味論での安全性と一致する。
- `ir_rel` は、型の注釈を除いて `SModel` を一意に決める（後述の「型の注釈」）。

信頼の対象は、`ir_rel` の定義がIRの意味として正しいこと、JSONの構文解析（`serde_json`）と、`serde_json::Value` から `Json` への機械的な変換だけになる。

## 対応の範囲

`ir_rel` は次を対応させる（`docs/ir.md` の「モデル」「型と値」「式」）。

- 列挙型：名前とラベルの列。`sm.enums` はラベルの数。
- 定数：名前、型、値の式。
- 状態変数：`id`（あれば添字と一致）、名前、型、`initial` または `initial_in`。
- 初期条件 `initial_constraint`。
- 操作：名前、`params` と `choices`（名前、型、`in`）、`guard`、`updates`（`target`、`expr`）、`output`（`type`、`expr`）。
  `in` を持つ引数は、guardの前に `contains` の検査を置く（`fmspec-ir` の組み立てと同じ形）。
  `n_params` は公開引数の型の幅の和。
- 不変条件（名前、式）、遷移契約（名前、操作の名前、式）、終端条件。
- 型：Bool、Int、Enum（名前で参照）、Tuple、Record（フィールドの名前は表の番号）、Option、Set、Map、List。
- 式：`docs/ir.md` の「式」の節のすべての演算子。
  - `{"local": 名前}` は、内側から探して最初に見つかった束縛の番号（外側から数える）。
  - `{"param": i}` は `Arg(i)`、`{"choice": i}` は `Arg(公開引数の数 + i)`。
  - `{"enum": {"type", "variant"}}` は、列挙型とラベルの番号。
  - `{"const": 名前}` は定数の番号。

名前の表は、列挙型、ラベル、定数、状態変数、操作、引数、不変条件、遷移契約、Recordのフィールドの名前を持ち、検査の条件や証拠を名前で読むときと、結果を表示するときに使う。
`ir_rel` は表の名前もJSONと対応させ、同じ種類の名前に重複がないことを確かめる。

範囲の外に置くもの：

- `ir_version`、モデルの名前、ソース位置（`source`）。意味に関わらない。
- 受理の条件（未知のキー、`in` の式が参照できる引数など）。拒否すべきモデルを拒否するのは `fmspec-ir` の仕事で、`ir_rel` は受理したモデルの意味を定める。
- 対称性の宣言（`symmetry`）。置換がモデルの対称性であることは判定ゲートが確かめる。
- 詳細化の写像の式。写像の意味保存は、今も述べていない。

### 型の注釈

`SModel` の式の一部は、オペランドの型から決まる注釈を持つ（`contains` の Set と List の区別、`SetContains` などの要素の型、量化の `Over` の種類とキーの型）。
これらはJSONに書かれていないので、`ir_rel` は注釈を制約しない。
注釈は中核の型付け `type_of` が検査し、型の付くモデルでは一意に決まる。
この一意性を補題として示すかは、手順4で判断する。

## 手順

1. **JSONの木と名前の表**：中核に `Json`（`Null`、`Bool`、`Int(i64)`、`Str(Vec<char>)`、`Arr`、`Obj`）と `IrNames` を置く。`fmspec-ir` に `serde_json::Value` からの変換を置く。
2. **関係の定義**：型の対応 `ty_rel`、式の対応 `ex_rel`（局所変数の名前の列を文脈に持つ）、モデルの対応 `ir_rel` を spec で書く。
3. **検査の実装と証明**：`check_ty`、`check_ex`、`check_ir` を exec で書き、`true` なら関係が成り立つことを証明する。`load_checked` を置く。
4. **一意性**：`ex_rel` が注釈を除いて式を一意に決めることを示す。可能なら、型の付く式では注釈も一意であることを示す。
5. **組み込み**：`fmspec-ir` の `parse_value` で、`lower_model_map` の代わりに `load_checked` を通す。対応しなければ内部エラーにする。
6. **テスト**：例のモデルと、ランダムに生成したIRがすべて通ることを確かめる。名前解決にわざと誤りを入れた `SModel` を拒否することを、単体テストで確かめる。
7. **文書**：`docs/verification.md` の信頼基盤、`fmspec-ir` の冒頭の説明、変異と `assert(false)` を更新する。この計画書は結果の記録に書き換える。
