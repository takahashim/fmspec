# 証明の対象と信頼基盤

fmspecの判定のうち、何を機械証明で保証し、何をテストで検査し、何を信頼しているかを示す。
[設計仕様書](ruby_model_checker_spec.md)§14.3が求める、証明済みの定理と未検証部分の一覧にあたる。

## 判定の意味

利用者が受け取る判定は、`fmspec-core` の `decide`（判定ゲート）だけが作る。
`decide` の事後条件 `verdict_sound` が、各判定の意味を定める。

| 判定 | 保証 |
|---|---|
| `Verified` | 証拠は証明書であり、`safe(m, c)` が成り立つ |
| `Violated` | 証拠はトレースであり、そのトレースは初期状態の1つから始まって有効（`trace_ok`）で、末尾で主張どおりの違反が起きる（`claim_holds`） |
| `Error` | 証拠はトレースであり、そのトレースは初期状態の1つから始まって有効で、末尾で主張どおりの評価エラーが起きる |
| `Inconclusive` | モデルについて何も主張しない。`decide` は証拠が得られなかった場合に限って返し、`CertCheck` は証明書の検査を打ち切った場合に返す |
| `InvalidModel` | モデルが整形式でない場合に限る |
| `Rejected` | 証拠が提示された場合に限る |

`safe(m, c)` は、検査条件 `c` の下で、いずれかの初期状態から対象の操作の遷移で到達できるすべての状態について、次が成り立つことである。
初期状態は1つ以上あり、整形式性 `wf` がそれを要求する。

- 対象の不変条件がすべて真に評価される。
- 対象の操作とドメイン内の引数のどの組でも、適用が評価エラーにならず、有効な遷移は対象の契約をすべて満たす。
- デッドロック検査が有効なら、有効な遷移のない状態で終端条件が真に評価される。

これらの定義は `semantics.rs` にあり、探索器にも検査器の実装にも依存しない。

## 証明済みの性質

Verusで検証した定理と、仕様書§14.1の証明義務との対応を示す。
ファイルは `crates/fmspec-core/src/` にある。

| 証明義務 | 定理 | ファイル |
|---|---|---|
| IR Validation | `validate_raw` は、モデルが整形式（`wf`）であるとき、かつそのときに限り受理する | `typing.rs` |
| Type Soundness | `lemma_type_sound`：型の付いた式の評価は、型どおりの値になるか、オーバーフロー、0による除算、明示的な失敗（`Fail`）のいずれかで失敗する。局所変数と量化を含む式は `lemma_type_sound_l` が扱う。`lemma_step_typed`：整形式なモデルでは、型に従う状態からの遷移先は型に従い、失敗は式の評価の失敗か範囲外更新である | `typing.rs` |
| Evaluation Correctness | `eval` の結果は、意味論 `eval_spec` と一致する。除算と剰余は床除算で、絶対値の符号なし除算で計算した結果が意味論の `floor_div`、`floor_mod` と一致する | `eval.rs` |
| Transition Soundness / Completeness | `step` の結果は `step_spec` と一致する。`enumerate` は、有効な遷移だけを、ドメイン内のすべての引数について漏れなく返すか、評価エラーになる引数を1つ返す | `step.rs` |
| Lowering Preservation（§14.1の表の外） | `lemma_safe`：`lower_model` が返した中核のモデルが安全であることと、名前を解決したモデルが値の意味論で安全であることは同値である。式ごとの意味保存は `preserve.rs` にある。詳しくは「信頼基盤」の節で述べる | `model_safe.rs` |
| State Equality | 状態は符号化列そのもので、等価性は列の一致である。`lemma_decode_injective`：型に属する符号は値と一対一に対応する | `step.rs` |
| Certificate Soundness | `check_certificate` が受理したなら、証明書は帰納的で、`safe` が成り立つ | `cert.rs` |
| Trace Validity | `check_trace` が受理したなら、トレースの開始状態は初期状態の1つで、`trace_ok` と `claim_holds` が成り立つ。`lemma_trace_reach`：初期状態から始まる有効なトレースの各状態は到達可能である | `trace.rs` |
| Verdict Gate | `decide` と `decide_raw` は前提条件を持たず、判定は `verdict_sound` を満たす。`CertCheck` は証明書の検査を区切って進め、検査し終えたときだけ `Verified` を返す。型不変条件として、検査を終えた状態が性質を満たして遷移で閉じていることを保つ | `gate.rs` |
| MBT Candidate Soundness / Completeness | `mbt::Session` の型不変条件：候補の列は、初期観測とこれまでの応答のすべてと矛盾しない状態（`consistent`）の集合とちょうど一致し、空でない。`start` と `observe` はこの不変条件を保つ。`lemma_consistent_reach`：候補は、応答の数と同じ回数の遷移で初期状態から到達できる | `mbt.rs` |
| MBT Input Soundness | `common_inputs` が返す入力と、`check_input` が有効とした入力は、どの候補にもその入力の有効な遷移がある。有効な入力を持つ候補がないと報告したなら、どの候補にも有効な遷移はない | `mbt.rs` |
| MBT Conformance Failure Soundness | `observe` が `Failure` を返すのは、入力がどの候補でも有効で、応答を加えた列と矛盾しない状態がないときに限る。`start` の `Failure` は、初期観測と一致する初期状態がないときに限る。`InvalidInput` なら入力が無効な候補がある。`ModelError` と `ModelViolation` は、候補からの実際の遷移で起きる評価エラーと性質の違反である | `mbt.rs` |
| MBT Resource Limit Safety | 候補数の上限超過は `TooMany` で、不適合とは別の結果である。`Continue` 以外の結果では、候補と応答の列は変わらない | `mbt.rs` |

`lemma_safe_excludes_trace` は、安全なモデルに、主張の成り立つ有効なトレースが存在しないことを示す。
したがって、同じモデルと検査条件に対する `Verified` と、`Violated` または `Error` は両立しない。

検証済みの実行関数とループは、すべて `decreases` を持つ。
検査器は、モデルと証拠の大きさに対して停止する。

MBTの「応答と矛盾しない」は、観測するスロットの値の一致、入力（公開引数と注入する選択の値）の一致、戻り値の一致で定める。
観測値と戻り値をJSONからスロットの値に符号化する処理は `fmspec-api` にあり、証明の対象外である。

`Verdict`、`CheckedModel`、`mbt::Session` はフィールドが非公開で、`fmspec-core` の外では構築できない。
`fmspec-core` の公開関数は `requires` を持たない。

## 証明が空虚でないことの検査

`rake verus`（`rake verus:proof`）は、証明を通すだけでなく、次の検査も行う。

- 信頼する項目（`assume`、`admit`、`external_body`、`assume_specification` など）が `fmspec-core` に1つもない。
- 証明の対象外のコードは `impls.rs`（標準トレイトの手書き実装）だけで、判定の経路から呼ばれない。
- 公開関数が `requires` を持たない。

`rake verus:mutants` は、さらに次を検査する。

- 検査を1つ壊した変異163件が、すべて証明に失敗する。たとえば、証明書の検査で遷移先の所属を調べない、トレースの状態を照合しない、拒否した証明書で `Verified` を返す、MBTの候補の更新で遷移先の観測を照合しない、初期条件が偽の状態を初期状態に残す、といった変異である。
- 到達点に置いた `assert(false)` 102件が、すべて証明に失敗する。

変異と `assert(false)` の一覧は `rakelib/verus.rake` にある。
変種ごとに crate 全体を検証し直すので、すべて回すと数時間かかる。
CI では回さず、証明を変えたときに手元で、変えたファイルに絞って実行する（`VERUS_MUTANTS_FILES=cert.rs,trace.rs rake verus:mutants`）。

## テストで検査するもの

次は証明の対象外で、テストで検査する。

| 対象 | 検査 |
|---|---|

| シミュレータ（`fmspec-search`） | 同じ乱数列を使う参照実装との、トレースの比較 |

| MBTのセッション（`fmspec-search`） | 入力の無作為な選択と不適合の診断（モデルが許す結果の列挙）。仕様書§17.2.1の境界ケース、参照実装との候補集合の比較 |
| MBTのドライバ（`lib/`） | 意図的にバグを入れた実装での、検出と縮小 |

| モデル合成（`lib/`） | 展開したIRの名前空間、添字、同期した操作の引数、guard、更新、遷移契約。到達可能な状態の数が、同期のない直積と同期した積に一致すること。仕様をまたぐ不変条件の違反の検出。合成したIRは、普通のIRと同じく判定ゲートを通る |
| 並行するプロセス（`lib/`） | 展開したIRのプログラムカウンタ、ローカル変数、ステップのguardと更新。インターリーブの列挙で更新の消失を検出し、ロックがあれば検証できること。ステップを各インスタンスの1つのスレッドで実行すること、反例のスケジュールの再現、実装のロックで待たされたステップの未完了、スレッドを残さないこと |

| 移行（`lib/`） | 段階の状態変数と、段階へ進む操作、段階ごとの不変条件への展開。混在するバージョンのある移行で、段階を早く進める誤りの検出 |
| Rails統合（`fmspec-rails/`） | 決済、ジョブ、Webhookを持つアプリケーションでの4種類の変異の検出、隔離の失敗の検出。PostgreSQLでの分離レベル別の適合と不適合（READ COMMITTED、REPEATABLE READ、SERIALIZABLE）、行のロックを書き落とした仕様のスケジュールの未完了 |
| IRと証拠の読み書き（`fmspec-ir`） | 不正なIRの拒否、往復、参照実装との比較 |

| CLI（`fmspec-cli`） | 終了コードと出力 |
| Ruby DSL（`lib/`） | 生成したIRと期待するIRの比較、参照実装による意味の確認、誤用の拒否。仕様のブロックを具体的な値で実行した結果との比較（後述） |

参照実装（`reference/fmspec_reference.rb`）は、IRを直接解釈する小さなEvaluator、幅優先探索、証明書検査器で、Rustの実装とは独立に書いてある。
複合型の値は、スロットに下ろさず、RubyのArray、Hash、Setに近い値として扱う。
比較テストは、固定のモデルとランダムに生成したモデルについて、結果の種類、報告する事象、トレース、訪問状態、証明書の受理と拒否の理由、シミュレーションのトレースを突き合わせる。
参照実装に意図的な誤り（Optionの順序、Setの列挙順、`push` と `put` の検査の順序、量化でたどる順、範囲外更新の位置など）を入れると、比較テストが失敗することも確かめている。

### TLCとの比較

参照実装との比較は、同じ作者が書いた2つの実装を比べるので、意味論の解釈の誤りが両方に同じ形で入ると見つからない。
そこで、IRをTLA+に変換し（`reference/fmspec_tla.rb`）、独立に実装されたTLCの評価器と状態空間の探索の結果と、fmspecの結果を突き合わせる（`reference/test/tlc_test.rb`、`rake test:tlc`）。
変換は参照実装にもエンジンにも依存しない。

変換は、評価の失敗をTLA+の値として表す。
式は `<<"ok", 値>>` か `<<"err", 種類>>` に評価され、演算子はIRの評価の順序どおりに最初の失敗を伝える。
床除算と剰余は、TLA+の `\div`（除数が正の場合の床除算）から組み立てる。
TupleとRecordは列（Recordはフィールドの順）、Optionは長さ0か1の列、SetはTLA+の集合、Mapはキーの集合を定義域とする関数、ListはTLA+の列で表す。
TLA+の集合と関数の等しさは外延的なので、IRの構造の等しさと一致する。
量化は、Setの要素とMapのキーを、キー型の値を正規順に並べた列から選んでたどり、Listの要素を位置の順にたどる。
正規順は変換の側で独立に列挙するので、TLCの集合の内部の順序には依存しない。
操作の適用の評価エラーと遷移契約の違反は、事象を記録した後続のない状態への遷移として表す。
不変条件、有効な遷移の有無、終端条件の結果は、状態変数の関数として状態に記録するので、状態の数は変わらない。
TLCに到達できる状態をすべて書き出させ、値をIRの値のJSON（トレースと証明書の形）に直し、安全性の意味での事象を集めて、次を確かめる。

- fmspecが `verified` なら、事象は1つもなく、到達できる状態の集合が証明書の状態の集合と一致する。
- fmspecが `violated` か `error` なら、トレースの状態はどれも到達でき、末尾の主張はTLCの事象の1つである。
- さらに、反例は最短である。TLCに遷移も書き出させ（`-dump dot`）、初期状態からの最短の遷移回数（深さ）を求める。
  fmspecの探索は幅優先なので、報告する事象は「展開の段」が最小の事象の1つで、トレースの長さは段から決まる。
  深さ d の状態を展開するときに、操作の適用の評価エラー、デッドロック、終端条件の評価エラー（トレースの長さ d）、その状態から出る遷移の遷移契約（長さ d+1）、新しく見つけた深さ d+1 の状態の不変条件（長さ d+1）を調べる。
  初期状態の不変条件は、展開の前に調べる。

同じ段に事象が複数あるとき、どれを報告するかは探索の順序で決まるので、参照実装との比較テストに任せる。
幅優先探索の代わりに `simulate` の反例を与えると、最短でない反例を検出することを確かめている。

対象は、IRのすべての型、すべての演算子、動的ドメインである。
固定のモデル、評価の順序と床除算の境界の式、範囲外更新と更新の順序と遷移契約の境界のモデル、複合型の演算の評価の順序と失敗の境界の式、複合型の範囲外更新と動的ドメインのモデル、ランダムに生成したモデル（既定は、スカラー型のモデルと複合型のモデルをそれぞれ200個）を比べる。
TLCの整数は32ビットなので、中間の値を含めて絶対値が2^30を超えうるモデルは変換しない。
したがって、`overflow` はこの比較の対象外である。
量化で展開する値が256を超えるモデルも変換しない。
変換に意図的な誤り（負の除数での床除算、二項演算の失敗の伝播、範囲外更新の検査、`all` と `any` の打ち切りと失敗の順序、比較演算子、`put` のキーと `push` の要素の検査、Optionの正規順、Setをたどる量化の順序、範囲外の整数を調べるスロットの順、`at` の範囲）を入れると、比較テストが失敗することを確かめている。

TLCは、`rakelib/tlc.rake` の `TLA2TOOLS_VERSION` のリリースの tla2tools.jar を、SHA-256を確かめて使う。

### DSLの具体的な実行との比較

証明済みの定理は検証済みのIRについてのもので、利用者が書いたRubyの仕様についての主張ではない。
DSLがIRを組み立てる過程（`lib/fmspec` の `Builder` と `Expr`）の誤りは、参照実装との比較でも見つからない。
そこで、仕様のブロックを、記号式の代わりに具体的な値で実行し直す解釈器（`test/support/concrete_dsl.rb`）を書き、DSLが生成したIRを参照実装で評価した結果と比べる（`test/dsl_concrete_test.rb`）。
解釈器は、`Fmspec` の `Types`、`Expr`、`Builder` を使わず、型と値の意味を docs/dsl.md と docs/ir.md から独立に書いたものである。

Rubyは引数を先に評価するので、`a & b` の `b` の評価エラーを例外にすると、IRの打ち切りと合わない。
解釈器は評価エラーを、型を持ったまま失敗を表す値にする。
演算はオペランドの失敗を記述順に伝え、打ち切る演算（`&`、`|`、`implies`、`ite`、`all`、`any`、量化）は、使ったオペランドの失敗だけを伝える。
`let` は、本体で使わなくても値の失敗を伝える。

初期状態と、ランダムな状態と引数のそれぞれで、次を比べる。

- 状態変数の名前と型、操作の名前と引数の型、不変条件の名前、終端条件の有無
- 初期状態の集合
- 不変条件と終端条件の結果（真、偽、評価エラーの種類）
- 操作の結果。無効か、有効なら遷移先と出力と各遷移契約の結果、評価エラーなら、IRが報告した最初の失敗（箇所、状態変数、種類）が、具体的な実行で失敗した箇所の1つであること

どの更新から先に評価するかはIRの組み立て方の選択で、利用者の書いた仕様の意味ではないので、評価エラーは失敗した箇所の集合で比べる。

仕様は、DSLの語彙を一通り使う固定の仕様（受理と拒否、内部選択、出力、遷移契約、`preserves`、動的ドメイン、複合型の演算、評価エラー）と、DSLのソースをランダムに生成した仕様（既定は300個。`test/support/dsl_generator.rb`）である。
生成した仕様は、記号ブロックの構文検査がソースを読めるように、ファイルに書いてから読み込む。
DSLに意図的な誤り（比較演算子、Setの `&`、単項の `-`、`implies` の向き、`ne`、`min`、`first`、`shift`、`subset?` の向き、Mapの量化でたどる値、`put` の値、`let` の展開、受理と拒否の枝、guardの否定、2つ目以降のguardの脱落、動的ドメインに渡す引数）を入れると、比較テストが失敗することを確かめている。

`process`、`migration`、`responds`、`Fmspec.compose` による展開は、まだこの比較の対象外である。

実装との適合性検査（`Model#test`）の結果は、判定ゲートを通らない。
候補集合の更新は証明済みだが、Ruby側のドライバ、Binding、観測値の符号化は証明の対象外である。

探索器に不具合があっても、誤った `Verified` や `Violated` にはならない。
探索器が保証しないのは、判定への到達、反例の最短性、探索統計の正しさである。

## 信頼基盤

次は証明の外にあり、正しいものとして信頼している。

- Verus、SMTソルバー（Z3）、Rustコンパイラ、標準ライブラリに対する `vstd` の仕様。
- 通常のcargoビルドでghostコードを消去する、`vstd` とVerusのマクロ。
- IRのJSONを読んで、名前を解決したモデルを組み立てる `fmspec-ir`。名前の添字への解決、型付きの式の木の組み立て、証拠と値のJSONとスロットの列の相互変換を含む。定数と初期値の評価、初期状態の集合の計算、式を中核の式に下ろす変換は中核にあり、検証済みである。
- 仕様からIRを生成するRuby DSL。受理と拒否の条件式への変換、定数の埋め込み、記号ブロックの構文検査を含む。具体的な実行との比較テストで検査する（「DSLの具体的な実行との比較」）。
- RubyとRustの境界。Nupur、その下の `nupur_sys` と rb-sys、拡張のグルーコード。
- 結果を表示するCLIと `Fmspec::Result`。

複合型は中核の外で扱う。
中核の式が持つのは、`let` と局所変数、有限の整数区間での `forall` と `exists`、床除算と剰余、BoolとEnumを整数にする `Code`、番号付きの明示的な失敗 `Fail` だけである。
`fmspec-ir` は名前を添字に解決して型付きの式の木を組み立て、中核の検証済みの関数に渡す（`lowering.rs`）。
この関数は型を検査し直し、複合型の値を固定長のスロットの列に、複合型の演算をスロットごとの中核の式に下ろす。
評価の順序と失敗を値の意味論と一致させるために、失敗しうる部分式は評価の順に `let` で束縛し、打ち切る演算と量化の本体は独立に下ろす。
引数は、スロットの値を1つずつ列挙し、正規形でない組をguardで除く。
除くための式（`canon.rs`）は検証済みで、各スロットの値がスロットの型（BoolのスロットやIntの範囲など）に属するとき、値の列がある値の正規形の符号化であるときに限り真になる。
量化は位置を1つの整数でたどる。
型の全体、Setの要素、Mapのキーをたどる量化では、位置は値の正規順での番号で、束縛する値のスロットの式は番号から作る。
Listの要素をたどる量化では、位置は添字で、スロットの式はその位置の要素のスロットを選ぶ。

型付きの式の木には、複合型の値の上で評価する意味論を仕様として与えてある（`source.rs`）。
下ろしの正しさは、この意味論との一致として述べる。
下ろしは、型が合わないなど想定外の入力に `None` を返し、`fmspec-ir` はそれを内部エラーにする。
したがって、証明するのは `None` でない結果についての性質（部分正当性）である。

すべての種類の式について、下ろしが意味を保つことを証明した（`preserve.rs`）。
対象は、リテラル、状態変数、遷移後の状態変数、引数、出力、局所変数、定数の参照、整数の算術と比較、等価比較、否定、含意、`all` と `any`、条件式、`let`、TupleとRecordの構成と要素の取り出し、Optionの構成と有無の検査と中身の取り出し、Setのリテラル、要素を含むかの検査、要素の追加と削除、和、積、差、部分集合の判定、Mapのリテラル、`Map#get`、`Map#put`、`Map#delete`、キーを持つかの検査とキーの集合、Listのリテラル、添字での参照、先頭と末尾、`push`、`pop`、`shift`、要素を含むかの検査、Set、Map、Listの大きさと空かの判定、量化（型の全体、Setの要素、Mapのキー、Listの要素をたどるもの）を組み合わせた式である。
ここで「環境が対応する」とは、中核の環境にある状態、引数、出力、定数のスロットの値が、意味論の環境の値の符号化であることをいう。

- **述語**：環境が対応するとき、`lower_prop` が下ろした式は、意味論と同じ真偽値になる。意味論が失敗するなら、同じ失敗になる。
- **置く値**：環境が対応するとき、`lower_stored` が下ろした各スロットは、値の符号化になる。意味論が失敗するなら、各スロットは同じ失敗になる。値が置く場所の型に属さない（整数の範囲外）なら、どれかのスロットの値がスロットの型の範囲の外になるので、中核の範囲外更新の検査が検出する。

この証明は、次の検証済みの部品の上に組み立ててある。

- **束縛の列**：`let` の入れ子にした束縛の列は、束縛を元の順に評価し、最初のエラーで止まる（`bindings.rs`）。
- **番号の式**：整数の区間での番号、Optionの番号（空なら0で、中身は値があるときだけ評価する）、TupleとRecordの混合基数の番号は、中核の算術と短絡の規則どおりに評価される（`ranking.rs`）。
  下ろした番号の式は、値が型に属すればその値の番号になり、属さなければ−1になる（`slots.rs`）。
  同じ基数の列について、範囲内の桁の列が等しいことと、混合基数の番号が等しいことは同値である。
  値の読み込みで、符号から番号を計算する関数（区間、Optionの有無、桁のたたみ込み）も検証済みである。
- **値を置くスロット**：`store` は、値が型に属するかの検査と、正規形のスロットの式を作る。属するなら、スロットの値は正規形の符号化になる（`slots.rs`）。
- **Mapの読み込み**：番号の順に並べた行を `encode_map_rows` でスロットの列にする。番号ごとの有無と値は、元の行と一致する（`map_encoding.rs`）。
- **`Map#get` のスロット**：`select_flat_map_lookup` は、下ろしたMapのスロットの列から、有無の検査と値のスロットの式を作る（`map_lookup.rs`）。
  キーの番号が負か、その行の有無が偽なら、値を評価する前に `MissingKey` で失敗する。
  そうでなければ、値のスロットの式は、その番号の行の値と同じ値になる。
- **番号からのスロット**：`unrank` は番号の式から、正規順でその番号にある値の、正規形の符号化になるスロットの式を作る（`quant.rs`）。
  TupleとRecordは番号を床除算と剰余で桁に分け、Optionは0を空とし、1以上なら1を引いた番号で中身を作る。
- **量化でたどる順**：位置を0から順にたどる中核の量化は、位置の列から選んだ値を順にたどる量化と、同じ値と同じ失敗になる（`quant.rs`）。
  位置の列は、型の全体、Set、Mapでは型の正規順の列で、選ぶのはSetの要素やMapのキーがある位置である。Listでは要素の列で、選ぶのは長さより小さい添字である。
- **等しさ**：Set、Map、Listは正規形で符号化するので、型に属する2つの値が等しいことと、符号化が等しいことは同値である（`equality.rs`）。
  同じ型の値の符号化は位置ごとに同じ種類の値になるので、スロットを位置ごとに比べる式は型の不一致で失敗しない。
  ただし、Listの長さは整数のスロットに入るので、長さの上限が `0x7fff_ffff` を超えるListを含む型の等価比較は下ろさない。
- **Listの行**：Listのスロットは、長さのスロットと、上限の数の行に区切れる（`lists.rs`）。
  長さより前の行は要素の符号化で、後ろの行は要素の型の既定値の符号化である。
  添字で行を選ぶ式は、選んだ要素の符号化を表す。
  `push` は元の長さ、`pop` は新しい長さと添字が一致する行だけを置き換え、`shift` は行を1つずつ前に詰める。
  行をつなぎ直した列は、Listの符号化を表す。
  添字と長さは整数のスロットに入るので、長さの上限が `0x7fff_ffff` を超えるListの添字での参照と更新は下ろさない。
- **Mapの行**：Mapのスロットは、キーの番号の順に、有無のBoolと値のスロットからなる行に区切れる（`maps.rs`）。
  `Map#put` と `Map#delete` は、キーの番号と一致する行だけを置き換え、行をつなぎ直す。

式についてのこの結果の上に、モデル全体の下ろしが安全性を保つことを証明した。
`fmspec-ir` は、名前を解決したモデル（`smodel.rs`）を組み立てて、中核の `lower_model` に渡す（`model_lower.rs`）。
このモデルは、定数、状態変数、各状態変数の初期値の候補の式、初期条件、操作（引数、guard、代入、出力）、不変条件、遷移契約、終端条件を、型付きの式の木で持つ。
値の上の意味論として、初期状態、遷移、到達可能性、安全性（`s_safe`）を、値の環境で式を評価して定める。
`lower_model` は、次を行って中核のモデルを作る。

- 状態変数と引数の型を検査し、スロットの位置を決める。
- 定数の式を評価して値を求め、型に属さなければ誤りとする。
- 各状態変数の初期値の候補を評価して符号の集合にし、集合の直積をとって、初期条件で絞り込む。候補の組の数が上限（`MAX_INITIAL_CANDIDATES`）を超えるか、初期状態が1つもなければ誤りとする。
- 操作ごとに、guardの前に引数の正規形の判定を置き、代入と出力をスロットごとの式に下ろす。不変条件、遷移契約、終端条件を述語として下ろす。

`lemma_safe`（`model_safe.rs`）は、`lower_model` が中核のモデル `m` を返したなら、定数の値 `cv` について、どの検査条件 `c` でも `safe(m, c)` と `s_safe(sm, cv, c)` が同値であることを示す。
この証明は、状態の符号化の対応（`rel`）の上で、初期状態の集合が一致すること、対応する状態からの遷移が同じ結果（無効、失敗、遷移先）になること、不変条件と遷移契約と終端条件の真偽が一致することを組み合わせる。
引数は、正規形の判定を通るスロットの値の組と、型に属する値とが一対一に対応する（`lemma_canon_rel`、`lemma_rel_canon`）。

モデル全体の比較テストは残している。
これは、名前の解決や型付きの式の木の組み立てなど、証明の外にある `fmspec-ir` の部分を検査する。

`fmspec-ir` が組み立てたモデルは、必ず中核のIR検証を通る。
証明書とトレースは判定ゲートが検査するので、その読み込みの誤りが誤った `Verified` や `Violated` に変わることはない。
一方、IRの生成や読み込みの誤りは、利用者の意図と違うモデルを検査する結果になる。
これは比較テストとIR変換のテストで検査している。
証明済みの定理は検証済みのIRについてのもので、利用者が書いたRubyの仕様についての主張ではない。
生成されたIRは `Model#to_ir` で確認できる。

## Nupurの写し

RubyのC APIとのやりとりは、Makiriのバインディング層Nupurを通す。
Nupurは公開crateではないので、Makiri v0.17.0.rc3（コミット `9ec094cf`）の `nupur` と `nupur_sys` を `vendor/nupur` に写して同梱している。
写しは編集しない。

| 検査 | 内容 |
|---|---|
| `rake nupur:check` | 写しの各ファイルが、記録したSHA-256（`vendor/nupur.sha256`）と一致する。Makiriのチェックアウトは要らない |
| `rake nupur:upstream` | 記録した内容が、Makiriのチェックアウトにある固定コミットの内容と一致する |
| `rake nupur:lint` | 型で表せないNupurの規則を、固定コミットの `nupur_lints` で拡張に対して検査する |

`nupur_lints` は、GVLを解放した処理の中の `Cancel::requested` も報告する。
これは中断要求を問い合わせるためのNupurの関数だが、lintはNupurの関数を一律に「Ruby-freeと分かっていない」と扱う。
拡張では、この2か所を理由付きの `expect` にしている。
lintが直れば `expect` が満たされなくなり、`rake nupur:lint` が失敗する。

## 既知の制限

- 出力の型はBool、有界Int、Enumに限る。
- 証拠の検査の資源上限は、評価回数の上限による事前の見積もりである。検査の途中で実際の評価回数を数えてはいない。中断は証明書の検査の区切りでだけ確かめ、トレースの検査、`replay`、`shrink` は中断できない。
- 引数のドメインは値を1つずつ列挙する。広い整数範囲の引数や、要素の多いSetの引数を持つ操作は、列挙に時間がかかる。複合型の引数では、スロットの値の組を列挙して正規形でないものを除くので、正規形の値の数より多くの組を調べる。
- 式の入れ子の深さは、JSONの読み込みの上限（128段）で抑えている。Rust APIから直接組み立てた極端に深い式は、再帰でスタックを使い切る可能性がある。
- CI（`.github/workflows/ci.yml`）は、`rake` の検査をジョブに分けて実行する。push と PR ごとに `rake verus:proof` で証明を検査する。変異と `assert(false)` の検査（`rake verus:mutants`）は数時間かかるので、CI では行わない。
